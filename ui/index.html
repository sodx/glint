      Glint shows what your programs did

      Values, logs, SQL, exceptions, timings and LLM calls from PHP, Python, Node and the browser arrive here as they happen, grouped by project and run. Your coding agent reads the same events.

      Install once

      cargo build --release -p glintd -p glint-cli && target/release/glint install

      This starts glintd at login, makes glint() a global in every PHP, Python and Node program, reports their uncaught errors, and tells the coding agents it finds (Claude Code, Cursor, VS Code, Windsurf, Gemini CLI, Codex) about Glint. Open a new terminal, then check that everything answers:

      glint doctor

      SDKs send nothing in production: when APP_ENV or NODE_ENV is production, or GLINT_ENABLED=0. Events never leave this machine.

      Methods

      After glint install, glint() works in PHP, Python and Node without an import. In PHP the other methods live on Glint\Glint; in Python, Node and the browser they hang off glint. Pick a language once and every example below follows it.

      glint(value) send a value

      Sends one event per value. Arrays, dictionaries, objects and models arrive as foldable JSON; an exception passed this way is shown as an exception with its stack. It returns a handle for the methods below.

      $order = Order::with('items')->find($id);
glint($order);                       // one value
glint($request->all(), $order->total); // several, one event each
      order = db.orders.get(order_id)
glint(order)                         # one value
glint(request.json, order.total)     # several, one event each
      const order = await db.orders.find(orderId);
glint(order);                        // one value
glint(req.body, order.total);        // several, one event each
      const cart = await fetch("/api/cart").then((r) => r.json());
glint(cart);
      curl -s localhost:23600/v1/events \
  -d '{"kind":"core.value","payload":{"value":{"id":7,"total":129.5}}}'

      label, colour, size, hide

      Change how the events you just sent look: a label to find them by, a colour (gray, green, orange, red, blue, purple), a smaller or larger row, or hide them. glint expect can match on labels, even ones set afterwards.

      glint($order)->label('before save')->green();
glint($payload)->label('webhook')->small();
glint($secret)->hide();
      glint(order).label("before save").green()
glint(payload).label("webhook").small()
glint(secret).hide()
      glint(order).label("before save").green();
glint(payload).label("webhook").small();
glint(secret).hide();
      glint(cart).label("cart on load").blue();
      # label and colour travel in meta
curl -s localhost:23600/v1/events \
  -d '{"kind":"core.value","payload":{"value":{"id":7}},"meta":{"label":"before save","color":"green"}}'

      log(message, fields, level)

      A log line with structured fields. Levels are trace, debug, info, warn, error and fatal; error and fatal count as failures.

      Glint\Glint::log('payment retried', ['order' => $order->id, 'attempt' => 2], 'warn');
      glint.log("payment retried", {"order": order.id, "attempt": 2}, level="warn")
      glint.log("payment retried", { order: order.id, attempt: 2 }, "warn");
      glint.log("checkout step", { step: 2, coupon: form.coupon.value });
      curl -s localhost:23600/v1/events \
  -d '{"kind":"core.log","payload":{"message":"payment retried","fields":{"attempt":2}},"meta":{"level":"warn"}}'

      table(rows, columns)

      Rows as a table. Pass the columns to choose and order them; without them the keys of the first row are used.

      Glint\Glint::table($order->items->toArray(), ['sku', 'qty', 'price']);
      glint.table([{"sku": i.sku, "qty": i.qty, "price": i.price} for i in order.items])
      glint.table(order.items, ["sku", "qty", "price"]);
      glint.table(cart.items, ["sku", "qty", "price"]);
      curl -s localhost:23600/v1/events \
  -d '{"kind":"core.table","payload":{"rows":[{"sku":"A-1","qty":2},{"sku":"B-7","qty":1}]}}'

      exception(error)

      An error with its class, message and stack. The window shows the code around the line it was thrown from. glint(error) does the same.

      try {
    $gateway->charge($order);
} catch (Throwable $e) {
    glint($e);                       // or Glint\Glint::exception($e)
    throw $e;
}
      try:
    gateway.charge(order)
except Exception as err:
    glint(err)                       # or glint.exception(err)
    raise
      try {
  await gateway.charge(order);
} catch (err) {
  glint(err);                        // or glint.exception(err)
  throw err;
}
      window.addEventListener("error", (e) => glint(e.error)); // already done for you; for caught errors:
try { renderCart(cart); } catch (err) { glint(err); }
      curl -s localhost:23600/v1/events -d '{"kind":"core.exception","payload":{
  "class":"TypeError","message":"coupon is null",
  "frames":[{"file":"/srv/shop/cart.js","line":11,"fn":"total"}]}}'

      measure(name, fn) time it, nest what it sends

      Runs fn, sends how long it took, and returns what fn returns. Everything sent while fn runs nests under the measure, inner measures too, so a run reads as a call tree. In Node and Python the nesting follows await; in the browser only the synchronous part of fn nests.

      $total = Glint\Glint::measure('pricing', function () use ($cart) {
    $rates = Glint\Glint::measure('load rates', fn () => Rate::forCart($cart)); // nests
    return $cart->total($rates);
});
      def price():
    rates = glint.measure("load rates", lambda: Rate.for_cart(cart))  # nests
    return cart.total(rates)

total = glint.measure("pricing", price)
      const total = await glint.measure("pricing", async () => {
  const rates = await glint.measure("load rates", () => loadRates(cart)); // nests
  return cart.total(rates);
});
      const html = glint.measure("render cart", () => renderCart(cart));
      # a measure is an event with a duration; children name it as parent
curl -s localhost:23600/v1/events -d '[
  {"id":"m1","kind":"core.measure","payload":{"name":"pricing","duration_ms":38.9}},
  {"kind":"sql.query","parent":"m1","payload":{"sql":"select * from rates","duration_ms":3.4}}]'

      pause(reason) stop until you answer

      Stops the program at this line until someone presses Continue in the window (or C), or a coding agent answers through MCP. It returns the value given with Continue, for example {"approve": true}, or nothing. Stop raises GlintStop. pause returns at once when Glint is off or unreachable, and on CI unless GLINT_FORCE_PAUSE is set; after 5 minutes it gives up and carries on.

      $answer = Glint\Glint::pause("refund {$order->total} EUR for order {$order->id}?");
if ($answer['approve'] ?? false) {
    $gateway->refund($order);
}
      answer = glint.pause(f"refund {order.total} EUR for order {order.id}?")
if answer and answer.get("approve"):
    gateway.refund(order)
      const answer = await glint.pause(`refund ${order.total} EUR for order ${order.id}?`);
if (answer?.approve) await gateway.refund(order);
      const answer = await glint.pause("check the discount before charging");
if (answer?.discount) cart.discount = answer.discount;
      # 1. send the pause with an id you choose
curl -s localhost:23600/v1/events -d '{"id":"p-42","kind":"ctl.pause","payload":{"reason":"refund?"}}'
# 2. wait for the answer: 204 = still waiting (ask again), 200 = {"action":"continue","value":...}
curl -s "localhost:23600/v1/ctl/p-42?timeout_s=25"

      send(kind, payload, meta) anything else

      Sends an event of any kind as it is. Use it for SQL queries from your own query logger, HTTP calls, jobs, or kinds of your own (prefix them with x-).

      DB::listen(fn ($q) => Glint\Glint::send('sql.query', [
    'sql' => $q->sql, 'bindings' => $q->bindings, 'duration_ms' => $q->time, 'conn' => $q->connectionName,
]));
      glint.send("sql.query", {"sql": sql, "bindings": params, "duration_ms": 3.4, "conn": "postgres"})
      glint.send("sql.query", { sql, bindings: params, duration_ms: 3.4, conn: "mysql" });
      glint.send("x-shop.step", { step: "address", valid: form.checkValidity() });
      curl -s localhost:23600/v1/events \
  -d '{"kind":"sql.query","payload":{"sql":"select * from orders where id = ?","bindings":[7],"duration_ms":3.4}}'

      flush() make sure it was sent

      SDKs send in the background without slowing your program. A short script that exits right away is flushed for you on exit; call flush yourself before a hard exit or before checking results with glint expect.

      Glint\Glint::flush();
      glint.flush()
      await glint.flush();
      glint.flush(); // also done when the page is hidden or closed
      # each POST is stored before it returns

      configure address, on/off, project

      Usually you need none of this: the defaults find glintd, and the project is the git repository's name. Environment variables do the same for every language: GLINT_URL, GLINT_ENABLED, GLINT_PROJECT.

      Glint\Glint::configure(url: 'http://127.0.0.1:23600', enabled: true, project: 'shop');
      glint.configure(url="http://127.0.0.1:23600", enabled=True, project="shop")
      glint.configure({ url: "http://127.0.0.1:23600", enabled: true, project: "shop" });
      <script src="http://127.0.0.1:23600/v1/browser.js" data-project="shop"></script>
      curl -s localhost:23600/v1/events -d '{"project":"shop","kind":"core.value","payload":{"value":1}}'

      A project that vendors an SDK itself (from sdks/php, sdks/python or sdks/js in the Glint repository) uses its own copy instead of the global one.

      What Glint records with no code at all

      Uncaught errors. PHP still prints its error and exits with the same code, Python still prints the traceback, and a Node process still crashes as before. Glint only records them.

      PHPuncaught exceptions and fatal errors (out of memory, a parse error in an included file). Works for scripts, php-fpm, Valet, Herd and php -S -t public. PHP skips the prepend file for a php -S router script; for artisan serve Glint loads it anyway.
      Pythonuncaught exceptions in any thread.
      Nodeuncaught exceptions and unhandled promise rejections.
      Browserwith one tag in the page you are developing: uncaught errors, unhandled rejections, console.error and console.warn, failed requests and resources that failed to load.
      <script src="http://127.0.0.1:23600/v1/browser.js" data-project="shop"></script>

      Only pages on localhost, 127.0.0.1, *.localhost or *.test can send. Leave the tag out of production builds.

      Frameworks catch exceptions to render an error page, so those are never uncaught. Glint hooks into WordPress, Laravel, Django, Flask, FastAPI, Express and Next.js to report them anyway (see each one's page). For another framework, call glint($e) in its error handler.

      WordPress

      A WordPress site on this machine needs no plugin. Glint recognises a WordPress request and hooks in before WordPress loads, so every page, admin screen, REST call and cron run reports on its own:

      the requestmethod and path first, and at the end a summary: response code, time, number of queries, memory, the template file, the conditional tags that were true, and the main query
      SQLevery $wpdb query with the theme or plugin line that caused it and the rows it returned; database errors count as failures. Timings appear when SAVEQUERIES is on in wp-config.php.
      errorseach WP_Error as it is created, _doing_it_wrong(), deprecation notices from themes and plugins, and PHP warnings
      mailwhat wp_mail() sends (to, subject, body) and mail that failed, with the reason
      HTTPcalls made with wp_remote_get() and friends; failed ones count as failures
      RESTresponses with an error status, with the route and WordPress's error code. The block editor saves over REST, so "Updating failed" arrives here with the reason.
      browserthe browser script on the front end, in wp-admin and on the login page, so JavaScript errors, failed requests and console errors arrive too
      block editorinvalid blocks, with the saved HTML and what the editor expected, and the editor's error notices

      The editor heartbeat that runs every 15 to 60 seconds is left out. A site whose WP_ENVIRONMENT_TYPE is production is left alone. To keep only some of this, set GLINT_WP (a constant in wp-config.php or an environment variable) to a list such as requests,errors,mail,rest,editor; add hooks to count every action and filter that fired; off turns it all off. WP-CLI commands are reported when GLINT_WP_CLI is set.

      Methods for your code

      use Glint\WordPress;

WordPress::post($post_id);          // the post with its fields, meta, terms and permalink
WordPress::user();                  // the current user: roles, capabilities that are on, meta
WordPress::query();                 // the main WP_Query: vars, the SQL it ran, the posts it found
WordPress::query($custom_query);    // or any WP_Query
WordPress::hooks('save_post');      // what listens to a hook: priority, callback, file and line
WordPress::template();              // the template file in use and the theme
WordPress::conditionals();          // is_single, is_admin and the other tags that are true now
WordPress::options('siteurl', 'permalink_structure');
WordPress::queries();               // every query of this request as a table (needs SAVEQUERIES)

      Plain glint(), Glint\Glint::measure() and Glint\Glint::pause() work in themes and plugins as everywhere else. A pause in a template stops the page until you continue it here.

      Docker and remote machines

      Code in a container or on another machine has no glint install, and 127.0.0.1 there is not this Mac. Run glint docker in the project folder. It writes a copy of the SDKs to ~/.glint/sdk/container and prints the lines to add to the service in docker-compose.yml:

      glint docker                 # compose; --run for docker run, --devcontainer, --ssh HOST
          volumes:
      - /Users/me/.glint/sdk/container:/opt/.glint/sdk:ro
    environment:
      GLINT_URL: http://host.docker.internal:23600
      GLINT_PROJECT: shop
      GLINT_PATH_MAP: /var/www/html:/Users/me/shop
      PHP_INI_SCAN_DIR: ":/opt/.glint/sdk/php/conf.d"
    extra_hosts:
      - host.docker.internal:host-gateway

      Recreate the container and glint() works in PHP, Python and Node there, and uncaught errors arrive as they do on the Mac. PHP_INI_SCAN_DIR loads the prepend file, PYTHONPATH runs a sitecustomize.py, and NODE_OPTIONS imports the global; the command sets only the ones for the languages it finds in the folder (--lang to choose).

      GLINT_URLwhere glintd is. Inside a container the SDKs already try http://host.docker.internal:23600 when it is not set.
      GLINT_PROJECTthe project. A path like /var/www/html does not say which repository it is, so the command names the git repository of this folder.
      GLINT_PATH_MAPcontainer path:Mac path, several separated by commas. glintd rewrites file paths and stack frames with it, so the source view and Open in editor show the files on this Mac. Use --app-dir when your compose file mounts the code somewhere else.

      Docker on Linux

      Docker Desktop on a Mac passes host.docker.internal to the Mac's 127.0.0.1, so nothing else is needed there. On Linux, host-gateway is the Docker bridge, which glintd does not listen on. Set remote_addr in Settings, or in ~/.glint/config.toml, to the bridge address and restart glintd:

      remote_addr = "172.17.0.1:23600"

      That address only takes events: a program there can send and wait for its own pause, and cannot read events, settings or files. glintd retries every 10 seconds when Docker creates the bridge after it started. Do not use 0.0.0.0: every network this machine is on could then write events.

      Dev containers

      glint docker --devcontainer prints mounts, runArgs and containerEnv for .devcontainer/devcontainer.json. The path map there is ${containerWorkspaceFolder}:${localWorkspaceFolder}, so it fits any checkout.

      SSH

      Keep glintd on the Mac and open a reverse tunnel, so 127.0.0.1:23600 on the remote machine reaches it:

      ssh -R 23600:127.0.0.1:23600 devbox

      Or put RemoteForward 23600 127.0.0.1:23600 under the host in ~/.ssh/config; VS Code Remote SSH reads that file too. glint docker --ssh devbox prints the commands that copy the SDK there and the lines for the remote shell profile. Set GLINT_PATH_MAP only when the same code is also on the Mac; otherwise the files open only on the remote machine.

      Laravel

      A Laravel app needs no package and no code. When public/index.php, artisan serve, an artisan command or a queue worker runs inside a Laravel app, Glint hooks in as the app boots and reports:

      the requestone run per request with a summary at its root: method, route, controller action, views, response code, time, memory and number of queries. Everything else nests under it, so the call tree shows the request.
      SQLevery query with its bindings, time, connection and the line in your app that ran it. A query from a Blade view points at the template, not the compiled file.
      exceptionswhat the exception handler reports, with the request: URL, route, action and input (passwords, tokens and keys hidden)
      logseverything written with Log::, at its level, with the line that wrote it
      queue jobsin a worker each job is a run of its own, with its SQL and exception under it; a failed job counts as a failure. A job on the sync driver nests under the request that dispatched it.
      HTTP callscalls of the HTTP client (Http::get() and friends) that failed: connection errors, 4xx and 5xx

      How it gets in: Laravel defines its env() helper only when none exists and calls it while the configuration loads. Glint defines an identical env() first and hooks in on that first call. With a cached configuration (php artisan config:cache) the call never happens. Clear the cache in development, or require the SDK with Composer, and Laravel discovers its service provider:

      composer require --dev glint/glint

      An app with APP_ENV=production is left alone. GLINT_LARAVEL=off in the environment turns the integration off.

      Django

      A Django project needs no middleware and no settings. Glint hooks in when Django's request handler loads, under runserver, gunicorn, uvicorn or any other server, sync or async:

      the requestone run per request with a summary at its root: method, route, view, response code, time, memory and number of queries
      SQLevery query of every database connection with its parameters, time, rows and the line in your code that ran it; a failed query counts as a failure
      exceptionswhat Django turns into an error page, with the request it happened in
      logsrecords of your own loggers, and warnings and errors of Django's, with the line that wrote them
      HTTP callscalls made with requests or httpx that failed: connection errors, 4xx and 5xx

      It works through the Python shim from glint install, so a virtual environment needs nothing either. GLINT_FRAMEWORKS=off turns the framework hooks off.

      Flask and FastAPI

      Flask, FastAPI and other Starlette apps report on their own, like Django:

      the requestone run per request with a summary at its root: method, route, endpoint, response code, time, memory and number of queries
      SQLevery statement that goes through SQLAlchemy (also Flask-SQLAlchemy and SQLModel), with its parameters, time, rows and the line in your code that ran it
      exceptionsunhandled exceptions, with the request they happened in
      logsrecords of your own loggers, with the line that wrote them
      HTTP callscalls made with requests or httpx that failed

      Async endpoints keep their request: what an awaited function sends still nests under it.

      Express and other Node servers

      Every HTTP server in a Node process reports its requests: Express, Fastify, Koa or plain node:http. For Express, Glint also knows the route and catches errors:

      the requestone run per request with a summary at its root: method, route pattern, response code, time, memory and number of queries
      SQLqueries of pg, mysql2 and node:sqlite with their values, time, rows and the line in your code that ran them, also through a pool
      exceptionserrors that reach Express's error handling (thrown in a route or passed to next(err)), with the request. Glint looks before your own error handler, which still runs.
      HTTP callsfetch() calls that failed: network errors, 4xx and 5xx

      This comes with the Node shim from glint install (NODE_OPTIONS). Prisma is not hooked; send its queries yourself if you need them:

      const prisma = new PrismaClient({ log: [{ emit: "event", level: "query" }] });
prisma.$on("query", (e) => glint.send("sql.query", { sql: e.query, bindings: JSON.parse(e.params), duration_ms: e.duration }));

      GLINT_FRAMEWORKS=off turns these hooks off; NODE_ENV=production turns Glint off.

      Next.js

      next dev reports each page and route handler request as a run, with the SQL of pg, mysql2 and node:sqlite under it, failed fetch() calls, and the errors Next.js prints for a route, with the request. Requests for /_next/ assets are left out.

      Vite

      The Vite plugin puts the browser script on the dev server's pages with the right project name, so the browser's errors, failed requests and window.glint() markers arrive here. A production build stays as it is.

      // vite.config.js
import glint from "glint-sdk/vite"; // sdks/js in the Glint repository, or ~/.glint/sdk/js

      Options: glint({ project: "shop", url: "http://127.0.0.1:23600" }). Without them the project is the git repository's name and the address comes from GLINT_URL.

      Call tree and timing

      Wrap work in measure() and everything it sends nests under it. A checkout request then reads checkout → load order → select … instead of a flat list. Click the arrow left of a row to fold it. The bars on the right are a small waterfall: where in the run each piece started and how long it took. OpenTelemetry spans nest the same way.

      Glint\Glint::measure('checkout', function () use ($id) {
    $order = Glint\Glint::measure('load order', fn () => Order::find($id)); // its SQL nests here
    glint($order)->label('order');
});

      Checks with glint expect

      Markers you placed with glint() become a test. glint expect waits until events match each expectation, in order, and fails as soon as a program errors. It prints which event satisfied each line.

      glint expect 'label:cart payload.value.total>0' 'kind:sql.query text:"insert into orders"' \
             'label:"order saved" payload.value.paid=true' -- ./checkout.sh 7
      label:Xthe event's label, also one set afterwards with .label()
      kind:sql.query, kind:sql.*the kind, or a prefix
      text:refundthe payload contains it, in any case
      payload.value.total>0a dot path compared with = != > >= < <=; true, null and numbers are JSON
      has:payload.value.emailpresent and not null
      count>=2how many matching events are needed

      It exits with 0 when everything matched, 1 when something did not, and 2 when it could not check. Without -- command it also looks at the last 30 seconds and waits while you click through the app (--timeout). Other flags: --unordered, --allow-errors, -p project. Agents run the same check through the MCP tool glint_expect.

      Coding agents

      glint install registers Glint's MCP server with the agents it finds. Claude Code also gets hooks, so its session shows up here next to your program and Glint can tell it things:

      • At session start it learns that Glint records this project, that glint() needs no import, and which failures happened in the last day.
      • With each of your prompts it gets the failures that are new since the previous one. When you write "it's broken", it already has TypeError … cart.js:11.
      • When it wants to finish a turn during which your programs failed, it is sent back once to fix them or explain why they are expected. Failures in files it edited afterwards don't count.

      Both can be turned off in Settings.

      glint_last_errorthe newest failure with its stack and values
      glint_events, glint_event, glint_runsfilter events, read one in full, list recent runs
      glint_wait_forwait for the next matching event after an edit
      glint_expectcheck that markers arrived with the right values and nothing failed
      glint_pauses, glint_resumeanswer a program stopped at pause()
      glint_annotate, glint_showleave a note on an event; show you markdown or a diagram
      glint_llm_calls, glint_clearLLM calls with tokens and cost; start a clean view

      Does the agent use it?

      Glint keeps a log of what agents do with it: each MCP tool call (which agent, which tool, how long, how big the answer, whether it showed a failure) and each hook action (context given, stop guard fired, then fixed or explained). The log stays in Glint's database on this machine and is deleted with the events. Press G for the Agents view: per day and project, which agents connected, their calls by tool, how many failures an agent read and how soon. In a run, a failure an agent read says read by Claude Code 14:02; other rows say it when you open them.

      glint stats --days 7

      prints the same numbers. examples/agent-eval has a small experiment that has Claude Code fix seeded bugs with and without Glint and compares turns, time and success.

      To set it up by hand:

      claude mcp add --scope user --transport http glint http://127.0.0.1:23600/mcp
      glint hook --print-config

      Settings and data

      Open Settings with , or the gear at the top. There you choose how long events are kept and how many, which editor files open in, and whether coding agents hear about failures. Changes apply right away and are saved to ~/.glint/config.toml, which you can also edit by hand. An environment variable with the same name (GLINT_KEEP_DAYS, GLINT_EDITOR, …) wins over both, and Settings shows which ones are set that way.

      By default Glint keeps 7 days and at most 100,000 events. Every 10 minutes it deletes older ones and the database file shrinks with them, so it stays at a few hundred MB at most.

      Everything lives in ~/.glint: the database, the settings, the SDK copies and glintd.log.

      Secrets

      glintd replaces passwords, tokens and keys in every event before it stores it, so they never reach the database, this window or a coding agent, which sends what it reads to a cloud model. It works the same for every SDK, OpenTelemetry and glint pipe. An event that had secrets says how many were replaced when you open it.

      Two things are caught:

      • Values under keys that look secret, at any depth: names containing password, passwd, secret, api_key, authorization, cookie, private_key, access_key, credentials, and names ending in token or dsn. Case, _, - and dots are ignored, so X-Api-Key and apiKey count. Header pairs and SQL bindings count too: in WHERE password = ? the bound value is replaced.
      • Well-known shapes anywhere in text: Bearer tokens, JWTs, AWS AKIA keys, GitHub ghp_ and github_pat_, Slack xox, Stripe sk_live_, OpenAI and Anthropic sk-, Google AIza, PEM private keys, the password in postgres://user:pass@host, and password=... in log lines and SQL.

      A replaced value reads [redacted]; a known shape keeps its prefix, as in sk-ant-…[redacted], so you can still tell which key was used. A URL keeps everything but its password.

      Left alone on purpose: counters and sizes such as token_count, max_tokens and password_length, pagination cursors such as next_token, and ids such as session_id, because a debugging session follows them from event to event. Add any of them to the extra keys if you want them hidden.

      In Settings, under Secrets, you can add key names, add regular expressions (a group named s hides only that part), list keys that are never hidden, or turn redaction off. The same settings are redact, redact_keys, redact_patterns and redact_allow in ~/.glint/config.toml, or GLINT_REDACT, GLINT_REDACT_KEYS (comma separated), GLINT_REDACT_PATTERNS (one per line) and GLINT_REDACT_ALLOW in glintd's environment. Changes apply to events that arrive afterwards; stored events stay as they are.

      Adding a language

      Any language can send events today with an HTTP POST (the HTTP tab above). A real SDK is small, because glintd does the hard parts: storage, search, projects, worktrees, the UI and MCP. An SDK needs to:

      1. Build envelopes (kind, payload, origin with file and line of the caller) and send them in the background, in batches, never blocking or throwing into the program.
      2. Turn the language's values into JSON with types, cycles and depth limits (docs/PROTOCOL.md §3).
      3. Implement the methods above: value, label and the rest, log, table, exception, measure with nesting, pause, send, flush.
      4. Stay off in production and when GLINT_ENABLED=0.
      5. Pass the conformance suite, which checks all of this against a real glintd:
      glint conformance -- ruby sdks/ruby/conformance.rb

      For the zero-setup global and the uncaught-error capture, each runtime has its own hook. These are the ones Glint would use:

      RubyRUBYOPT=-r…/glint.rb in the shell profile loads it into every process; at_exit with $! sees uncaught exceptions.
      Gono global code injection: an import (glint.V(x)), with defer glint.Recover() for panics.
      Java, KotlinJAVA_TOOL_OPTIONS=-javaagent:glint.jar loads an agent into every JVM; Thread.setDefaultUncaughtExceptionHandler sees crashes.
      .NETDOTNET_STARTUP_HOOKS runs code before Main; AppDomain.UnhandledException sees crashes.
      Rusta crate with a glint!() macro that knows file and line; a panic hook for crashes.
      Elixir, Erlanga Logger backend and :telemetry handlers, so existing logs and spans arrive with no code.

      OpenTelemetry already covers many of these for traces and LLM calls. spec/conformance/README.md has the full checklist.
